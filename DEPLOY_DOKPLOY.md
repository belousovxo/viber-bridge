# Деплой Viber-моста через Dokploy

Инструкция для того, кто публикует мост (человека или LLM-ассистента). Настройку Chatwoot делает
владелец проекта, здесь её нет. Результат работы — URL моста и API-ключ, переданные владельцу.

## Что это и как устроено

Мост подключает обычные Viber-номера к Chatwoot. На отдельном сервере работают:

- **manager** — HTTP-сервис на порту 8800, единственное, что видно снаружи (через домен и HTTPS);
- **контейнеры `viber-session-<id>`** — по одному на каждый Viber-номер. Их создаёт и удаляет сам
  manager через Docker-сокет. В интерфейсе Dokploy их нет, и трогать их руками не нужно.

Всё описано в [manager/docker-compose.dokploy.yml](manager/docker-compose.dokploy.yml). При каждом
деплое собираются два образа: образ Viber (`viber-session:latest`, Viber скачивается с CDN и
сверяется по sha256 с проверенной версией 29.4.0.7) и manager.

## Что получить от владельца до начала

| Что | Зачем |
| --- | --- |
| Доступ к панели Dokploy | там создаётся сервис |
| Исходящий IP сервера Chatwoot | только ему откроем 443 |
| Доступ к репозиторию `viber-bridge` для Dokploy | источник для деплоя |

## 1. Сервер

Нужен **отдельный** VPS, не тот, где работает Chatwoot или панель Dokploy: manager получает доступ
к Docker-сокету, то есть root-права на своём сервере.

- архитектура **amd64 (x86_64)**: Viber под ARM не работает;
- Ubuntu 22.04 или 24.04, shell по умолчанию — bash;
- RAM: ~1 ГБ на систему плюс ~0,5 ГБ на каждый Viber-номер (4 ГБ хватит на 5–6 номеров);
- диск от 30 ГБ (образ Viber весит ~2,6 ГБ, при обновлении временно лежат два).

**Домен.** Выбрать поддомен для моста, например `viber-bridge.<ваш-домен>`, и создать A-запись на
IP этого сервера. Домен нужен для HTTPS: Let's Encrypt выдаёт сертификат только на домен, который
указывает на сервер. Без HTTPS ключ и сообщения пойдут через интернет открытым текстом.

## 2. Подключить сервер к Dokploy

1. *Settings → SSH Keys*: создать ключ, скопировать публичную часть.
2. Добавить этот публичный ключ на сервер (`~/.ssh/authorized_keys` пользователя `root`).
3. *Remote Servers → Add Server*: IP, пользователь `root`, выбранный ключ → *Create*.
4. В меню сервера *Enter Terminal*: если терминал открылся, связь есть.
5. *Setup Server* → вкладка *Deployments* → *Setup Server*. Делается один раз.
6. **Выключить Docker cleanup для этого сервера** (меню сервера → *View Actions*). Автоочистка
   делает `docker image prune -a` и может удалить образ Viber, когда номеров нет. После этого
   manager не стартует, а новые номера не подключаются.

## 3. Создать сервис

1. В проекте: *Create Service → Compose*, тип **Docker Compose** (не Stack).
2. **Server: выбрать сервер из шага 2.** По умолчанию стоит *Dokploy Server*, это неверно.
3. *Provider*: репозиторий `viber-bridge`, ветка `main`.
   **Compose Path:** `./manager/docker-compose.dokploy.yml`.
4. *Environment*:
   ```
   MANAGER_API_KEY=<сгенерировать: openssl rand -base64 32>
   ```
   Это пароль от моста: не публиковать, не коммитить, передать владельцу защищённым каналом.
   Опционально `SESSION_MEMORY=1g` — лимит памяти на один номер (по умолчанию 1g).
5. *Domains → Add Domain*: Host — домен моста, **Service — `manager`**, **Port — `8800`**,
   HTTPS включить, сертификат Let's Encrypt.
6. *Advanced*: Isolated Deployments не включать.
7. *Deploy*. Первая сборка занимает 5–10 минут.

## 4. Проверить (до файрвола)

Во вкладке сервиса должно быть:

- `manager` — *running (healthy)*;
- `viber-session-image` — **Exited (0). Так и должно быть**: этот контейнер только собирает образ.

С любой машины:

```bash
curl -s https://<домен>/health
# {"ok":true}
curl -s -o /dev/null -w '%{http_code}\n' https://<домен>/sessions
# 401   (без ключа мост не пускает)
curl -s -H "Authorization: Bearer <MANAGER_API_KEY>" https://<домен>/sessions
# []    (пока номеров нет)
```

## 5. Файрвол

Мост должен быть доступен только серверу Chatwoot. Настраивать в **файрволе провайдера**
(Hetzner Cloud Firewall, Security Groups и т.п.). `ufw` здесь не работает: Docker публикует порты
80/443 в обход его правил.

| Порт | Откуда |
| --- | --- |
| 22 | IP сервера панели Dokploy и IP администраторов |
| 80 | отовсюду (нужен Let's Encrypt для выпуска и продления сертификата) |
| 443 | **только** исходящий IP сервера Chatwoot |

Исходящий трафик не ограничивать: Viber и manager ходят в интернет и в Chatwoot.

После этого `curl https://<домен>/health` с вашей машины перестанет отвечать — это нормально.

## 6. Передать владельцу

- URL моста: `https://<домен>`
- `MANAGER_API_KEY` — защищённым каналом

Дальше владелец сам подключает мост в Chatwoot.

## 7. Бэкап

В томе `manager-data` хранится реестр: какой номер к какому inbox'у привязан, и секреты webhook'ов.
Если он потеряется, контейнеры продолжат работать, но сообщения перестанут доходить, и ошибок при
этом не будет.

Dokploy: *Volume Backups* сервиса → том `manager-data` (в Dokploy имя может быть с префиксом
проекта), назначение — S3-хранилище из *Settings → Destinations*, раз в сутки.

## Эксплуатация

- **Обновление моста:** *Redeploy*. Пересоберутся оба образа, manager перезапустится и сам
  переведёт работающие номера на новый образ, повторно сканировать QR не нужно. Viber при этом
  убивается жёстко, поэтому делать это в спокойное время.
- **Не трогать руками:** контейнеры `viber-session-*`, тома `viber-*`, сеть `viber-sessions`.
  Ими управляет manager. Не запускать на сервере `docker system prune` / `docker volume prune`.
- **Посмотреть номера** (терминал сервера в Dokploy):
  `docker ps --filter name=viber-session- --format '{{.Names}}\t{{.Status}}'`
  и `docker stats --no-stream`.

## Если что-то пошло не так

| Симптом | Что делать |
| --- | --- |
| Сборка падает: `viber.deb is not Viber 29.4.0.7` | Viber выпустил новую версию, на ней мост не проверен. **Не менять версию в Dockerfile.** Сообщить владельцу: он даст файл `viber.deb` нужной версии ([session/vendor/README.md](session/vendor/README.md)). |
| manager перезапускается, в логах `session image viber-session:latest not found` | Образ удалён (скорее всего, автоочисткой). Выключить Docker cleanup (шаг 2.6) и сделать *Redeploy*. |
| manager перезапускается, в логах `MANAGER_API_KEY` | Не задана переменная в *Environment*. |
| Сертификат не выпускается | Проверить A-запись и что порт 80 открыт для всех. |
| `exec format error` при сборке или старте | Сервер не amd64. Нужен x86_64. |
